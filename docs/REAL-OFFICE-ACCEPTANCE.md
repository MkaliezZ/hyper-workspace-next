# Office 双执行器真实模型检查

2026-11-10（美国太平洋时间），使用实际 DeepSeek `deepseek-flash`、固定 DSH/Hermes 原生执行器与 Collabora 26.04.6.1 / 官方 pyuno，完成六个“起草方案 → 核对 → 确认新副本 → 下载校验”样例。业务核心与内核代码基于 `f492cc7`；随后增加的透视表支持独立验证，不从这些模型样例推导。

来源是隔离测试库和合成回环 DAV，文件是仓库合成素材。实际 Nextcloud、多人浏览器与部署由对应 CI 单独证明；本记录不是公司资料或公司安装验收。

| 执行器 | 格式 | 实际保存与独立检查 |
| --- | --- | --- |
| DSH | DOCX | 替换指定段落，原件不变；其他段落、加粗、表格保留 |
| DSH | XLSX | 修改 Report!B5，在已检查的 B4 写跨表求和公式，回读 40；原公式、筛选、验证、图表保留 |
| DSH | PPTX | 替换指定文本框，原件不变；两页及表格保留 |
| Hermes | DOCX | 同一方案/确认服务与上述段落、加粗、表格检查 |
| Hermes | XLSX | 同一服务写 B5/B4，公式结果 40 与工作簿结构检查 |
| Hermes | PPTX | 同一服务完成两页与表格检查 |

每次起草没有来源 PUT。脚本核对操作数量、确切目标、预期旧值和新值后，才作为合成测试操作人确认该版本。确认后只出现一次条件新建，原文件字节保持不变，新文件 SHA-256 与产品回执一致。另一员工不能读取方案或执行记录。同一 Run 重放未产生第二份副本。

## 首轮失败与用量

首轮 DSH 的 DOCX 两次请求通过。随后表格请求还指定了检查范围之外的 B6；模型只返回 B5 的修改，方案完整性检查失败，脚本没有确认这份不完整方案。失败保留在首轮报告。后续改用检查结果中已有的空白 B4，运行剩余五个格式/执行器组合，没有重新调用已通过的 DSH DOCX。

两轮共 13 次实际供应商请求：12 条用量 `reported`、1 条 `partial`，13 条费用均为 `unpriced`。账本已记录输入 51885、输出 4152 token；由于一条统计不完整，这不是完整供应商账单。最终六份副本通过，不把首轮不完整方案写成成功。

## 复查入口

`npx tsx scripts/real-office-smoke.ts` 默认仅输出预检，不连接数据库、启动内核或请求模型。实际执行需要已有固定原生运行时、可达的真实 Office 服务、隔离 `*_test` 数据库、文档检查 Python 和环境中的供应商凭据，再显式使用 `--execute`。凭据不作为命令行参数。

默认最多执行六组、十二个业务 Run；`REAL_OFFICE_CASES` 可选未完成的组合，例如 `dsh:xlsx,hermes:xlsx`。没有自动重试已发出的供应商请求。此脚本不负责公司身份、原件、服务器或编辑器会话配置。模型样例只证明指定输入的结果；全量文件兼容范围见 [Office 能力边界](../runtime/office/COMPATIBILITY.md)。
